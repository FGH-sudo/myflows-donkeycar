# 剩余 4 个 dW GEMM：结果不变的 split-K 归约与 cp.async 多级流水

## 结论

[gate-profile-003](../gate-profile-003/report.md) 留下 4 个超过 register/cuBLAS ≤ 1.20 的 ResNet18 dW GEMM。本次做了两项改动，输出与改动前逐位相同：

1. split-K 归约仍返回固定顺序 FP64 求和的结果，但不再逐元素做 FP64 运算：2 份切分用 FP32 计算，3–32 份切分用 64 位整数精确求和，只有少数输入回到原 FP64 循环；
2. 为 TN 布局（权重梯度）增加 cp.async 多级流水的 register kernel，作为 3 种新 tile。

4 个形状的计划只换 tile，切分数不变；3 个切分形状的 K 块宽度也不变，不切分的 512×256×640 由 k16 改为 k32（不切分时每个输出按 k 递增顺序累加，与 tile 无关）。下表是生产调用路径在 Nsight Compute 锁频计数下的比值（candidates-001，每项交替 5 次取中位数）：

## 1. split-K 归约

### 原来的瓶颈

原 kernel `gemm_split_reduce` 对每个输出计算 `(float)(((0.0 + p0) + p1) + … + p[S−1])`，每个切片一次 FP32→FP64 转换和一次 FP64 加法。[gemm-ncu-001](../gemm-ncu-001/report.md) 测得 FP64 流水线活跃 50%–83%；每个 FP64 warp 指令在 SM 上占用约 16 个周期，GeForce Ada 的 FP64 吞吐只有 FP32 的 1/64。

### 两份切分：FP32

p0 + p1 先舍入到 binary64 再舍入到 binary32，与直接舍入到 binary32 结果相同：加法的二次舍入在 53 ≥ 2·24 + 2 时无害。`0.0f + p0` 与 `0.0 + p0` 一样把 −0 变成 +0。上溢与下溢的处理和 FP64 路径相同；IEEE 次正规数要求编译时不开 `-ftz`，DLL 正是如此编译。唯一不同是 NaN：FP32 加法返回规范 NaN，FP64 路径保留输入的 payload。因此结果为 NaN 时用原 FP64 循环重算。这个函数不能内联：内联后编译器把回退分支转成谓词执行，每个线程都做 FP64 运算，耗时不变（25.6 µs）。改成 `__noinline__` 后为 12.2 µs。

### 3–32 份切分：整数精确求和

设 lo、hi 为非零切片中最小和最大的指数域（次正规数记为 1）。每个切片都是 u = 2^(lo−150) 的整数倍，绝对值小于 2^(hi−126)。若 hi − lo ≤ 29 − ⌈log₂S⌉，原循环的每个部分和都是 u 的整数倍且绝对值小于 2^53·u，可以在 binary64 中精确表示。于是每次 FP64 加法都是精确的，原循环的结果等于精确和舍入一次（和为 0 时为 +0）。

新 kernel 以 u 为单位把各切片换成 64 位整数相加（整数加法与顺序无关），用 `cvt.rn.f32.s64` 舍入一次，再通过指数域乘以 u。结果为正规数时这一步是精确的。以下情况回到原 FP64 循环（与原 kernel 同一段代码）：指数跨度超出上述范围、出现 Inf 或 NaN、结果为次正规数或上溢。

每个输出由 G 个 lane 分担切片，先用 warp shuffle 合并 lo、hi 与 Inf/NaN 标志，再合并整数和。实测只有小输出、多切片时（128×64，11 份）2 个 lane 更快，其他情况 1 个 lane 持有全部切片；4 或 8 个 lane 时同一条访存指令覆盖的连续元素变少，反而更慢。48 份以上的小输出仍用原来的 8 warp 并行 FP64 归约。

### 验证

- 原型：切片数 2–32 共 15 种，每种 120,000 列，覆盖普通梯度、指数跨度恰在范围内与超出 1–2、正负零、次正规数、接近上溢、相互抵消、舍入恰在中点、随机位模式（含各种 NaN payload）、零星 Inf/NaN。与 FP64 kernel 的输出逐位比较（含 NaN payload），差异为 0。
- 原型测量时发现：CuPy 的 `RawModule` 总会追加 `-ftz=true`，这样编译的 FP64 循环会把次正规切片清零（2^−126 − 2^−127 得到 2^−126），一开始看起来像新 kernel 出错。DLL 不开 `-ftz`，以上证明与测试都以 IEEE 次正规数为前提；原型改用与 DLL 相同的 NVRTC 选项。
- 单元测试（`MyFlows/tests/test_cuda_native_kernels.py` 新增 `NativeSplitReduceTests`）：
  - 11 种切片数 × 3 种输出（含不足一个 warp 的输出与两 lane 情形），新归约与原 FP64 kernel（`native.split_reduce(..., reference=True)`）逐位相同，原 kernel 与 NumPy 的 FP64 循环逐位相同（NaN 只比位置）；
  - 5 个切分 GEMM（含 NN、NT）的输出，等于各 K 段单独计算后用原 FP64 kernel 归约的结果；
  - 每种 cp.async tile 在 3 个对齐但不整除 tile 的 TN 形状、3 种切分数下，与上述参考逐位相同。其中 K = 100 切 7 份时，每段只有一个 K 块，少于流水级数。

## 2. TN 布局的 cp.async 多级流水

TN 布局下 A 按 K×M、B 按 K×N 存放，BK×BM 与 BK×BN 的每一行在全局内存中都是连续的，cp.async 可以不经寄存器、不转置地直接拷到共享内存。原 kernel 用寄存器双缓冲，只有一个 tile 在途。split-K 的每段只有十几个 K 块，每个块的计算远短于 DRAM 延迟，于是每一步都在等访存。新模板 `gemm_async_tn` 保持 STAGES − 1 个 tile 在途。越界的行与列用源大小为 0 的拷贝填零，共享 tile 的内容和 FMA 的 k 顺序与 `gemm_register` 完全相同，因此结果逐位相同；sm_80 以下退回 `gemm_register`。

新增 3 种 tile，名称以 `/s<级数>` 结尾：`32x64/4x4/k32/s2`、`64x64/8x4/k16/s3`、`64x64/8x4/k16/s4`。它们只有 TN float4 kernel 走流水，其他布局与对齐方式就是普通 register kernel。

| 形状（切分） | 原 GEMM kernel µs | 新 GEMM kernel µs | cuBLAS µs |
| --- | ---: | ---: | ---: |
| TN 128×64×2560（11） | 18.21 | 14.08 | 13.31 + 归约 4.06 |
| TN 512×256×640（1） | 51.01 | 44.22 | 38.37 |
| TN 256×128×2560（6） | 40.67 | 33.25 | 34.14 + 归约 6.91 |
| TN 256×1152×2560（2） | 261.50 | 256.83 | 237.73 |

原型中流水级数并不是越多越好：TN 512×256×640 上 32x64 的 6 级为 59.4 µs，3 级为 45.0 µs。64x128/8x8 的 3 级流水需要 36 KB 共享内存，每个 SM 驻留的 block 减少，2 份切分时为 318.9 µs，比寄存器版本（261.6 µs）还慢，因此没有采用。

其他检查：

- 现有 131 个 kernel 的 PTX 在改动前后逐条相同（只有基本块编号不同），未改计划的形状运行的代码不变；
- NVRTC 冷编译从约 15.0 s 增加到 17.9 s（156 个 kernel），之后按源码哈希命中磁盘缓存；
- 内嵌源码每段都小于 16 KB（最大 8.8 KB）。

## 3. 候选与计划

用 `python -m benchmark.gemm_ncu --shapes TN:128:64:2560,TN:512:256:640,TN:256:128:2560,TN:256:1152:2560 --candidates` 搜索全部 20 种 tile 与可用的切分数，结果在 candidates-001。采用的 4 项计划见开头的表。另有两个更快的候选会改变切分数（舍入随之改变），没有采用：

- TN 512×256×640：64x64/8x4/k16/s3 切 2 份，1.124；
- TN 256×1152×2560：64x64/8x4/k16/s3 不切分，1.098。

改动前后计划的切分数相同。3 个切分形状的 K 块宽度也相同（11 份每段 240、6 份每段 432、2 份每段 1280），各段部分和逐位相同，归约结果也逐位相同；不切分的 512×256×640 由 k16 改为 k32，每个输出仍按 k 递增顺序做 FMA，结果与 tile 无关。整网验证见 before-after-001（根仓库 de1f1e6、MyFlows f9344b5 的工作树与当前代码，ResNet18 w16 batch 128，3 个 batch）：numpy、cupy、native、register 四种配置在 3 个 batch 上的 82 个梯度数组与 loss，改动前后逐位相同。

w16 batch 128 的网络只含 4 项计划中的 TN 128×64×2560；另外 3 项（256×128×2560、256×1152×2560、512×256×640）属于 w64 batch 32，整网对拍没有覆盖。合并前复核时直接比较了这 4 个生产形状。每个形状用 4 组随机 FP32 输入：一半元素为 ReLU 零，其中 2 组按 K 行乘以 2^−20 到 2^19 的随机比例。新计划、按计划表的默认调用、旧计划三者的输出，都与旧引擎的结果逐位相同（旧 tile 逐段不切分计算，再用原 FP64 kernel 归约），共 16 组。w64 的整网对拍没有运行。
