# 卷积 GEMM 的锁频内核对比与计划修正

## 为什么改用 Nsight Compute

事件计时的门槛在同一次运行内就不稳定：gate-profile-002 中同一 GEMM 的 6 轮 register 耗时可以从 0.066 ms 到 0.133 ms，64 个形状的轮间极差中位数为 36.4%。它报出的 8 个超限形状里，多数形状的 tile 与切分和上一轮完全相同。规划 2.3 节规定，单个 kernel 的比较用 Nsight Compute 的 `sm__cycles_elapsed.max`，不用墙钟时间。

`benchmark/gemm_ncu.py` 的做法：

- `--clock-control base` 把 GPC 时钟锁在基频（本次实测 SM 1.544 GHz），`--cache-control all` 在每个 kernel 前清空 L1/L2；
- 每次 GEMM 调用包在一个 NVTX 区间内，区间内的 GEMM 与 split-K 归约 kernel 求和；
- register 与 cuBLAS 交替调用 7 次，取周期数中位数之比。

同一调用 7 次的极差中位数为 4.0%，第 2 到第 6 位之间的离散为 1.0%。

## 候选计划搜索

对每个超限形状列出全部已编译 tile 与能产生不同切分数的请求值，先用 5 轮打乱顺序的 CUDA Event 取最短时间做预筛（降频只会增加耗时），再把前 12 名和最快的不切分计划放到 Nsight Compute 下交替测 5 次（`python -m benchmark.gemm_ncu --shapes <布局:M:N:K> --candidates`）。结果在 candidates-001。

| 形状 | 原计划比值 | 最好的候选 | 候选比值 | 处理 |
| --- | ---: | --- | ---: | --- |
| TN 128×64×2560 | 1.498 | 64x32/4x4/k16 / 13 | 1.466 | 保留原计划（候选只快 2%，且改变舍入） |
| TN 32×288×38400 | 1.401 | 32x32/4x4/k16 / 16 | 1.044 | 采用 |
| TN 256×128×2560 | 1.331 | 128x64 / 6 | 1.240 | 采用（切分不变，输出逐位相同） |
| TN 512×256×640 | 1.333 | 原计划即最快 | 1.332 | 保留 |
| NT 38400×32×288 | 1.240 | 64x32/4x4/k16 / 1 | 1.064 | 采用（不切分，输出逐位相同） |
| TN 256×1152×2560 | 1.192 | 原计划即最快 | 1.192 | 保留 |

原 NT 38400×32×288 计划在 N = 32 的输出上使用 64 列的 tile，一半线程没有输出。

## 一次被测量否定的归约改动

TN 128×64×2560 的 register 调用由 GEMM kernel（18.3 µs）与 split-K 归约 kernel（7.8 µs）组成，cuBLAS 的两个 kernel 分别为 13.3 µs 和 4.2 µs。最初假设归约受每个切片一次的读延迟限制，于是把每 8 个切片的读取提前到按原顺序的加法之前。14 组顺序与并行归约的输出逐位不变，但归约反而变慢：11 个切片 7.78→9.50 µs，6 个切片 10.62→12.70 µs，2 个切片（1152 个线程块）25.66→80.03 µs。该改动已撤回，测量保存在 candidates-002-grouped-reduce。

随后在原 kernel 上采集流水线指标（reduce-fp64）：FP64 流水线活跃比例在 11、6、2 个切片时分别为 50%、70%、83%，DRAM 吞吐只有峰值的 20%–49%。每个元素每个切片都要做一次 FP32→FP64 转换和一次 FP64 加法，GeForce Ada 的 FP64 吞吐很低，归约因此受 FP64 流水线限制。固定顺序的 FP64 归约是为确定性和单次舍入有意保留的设计，本次不改。
